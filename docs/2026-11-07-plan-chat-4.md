# Etappeplan for kode15.studio (chat 4, 07.11.2026)

Revidert samme dag etter Jørns korreksjon: raven er webserveren
(ingen VPS/backhaul), FortiGate er kontrollpunktet, swarm og hybrid
LLM (RTX 5080/5090) er utbyggingstrappen. Rammen står i
`docs/2026-11-07-aapen-kant-beslutningsnotat.md`.

Chatten blir i `studio15-light` til Handover 0 ligger i
`KODE15studio/studio`. Light kjører urørt gjennom alle etappene.

## Ferdig 07.11

- Org-vedtaket (`docs/2026-11-07-org-struktur.md`): én org
  `KODE15studio`, vaktmesteren installert og verifisert
  (installasjon `179558664`), tomme repoer `studio` og `mal-studio`.
- Etappe 1: beslutningsnotatet for åpen kant er skrevet — venter på
  Jørns svar på de fem beslutningspunktene nederst i notatet.

## Etappene

**E1 — Beslutningsnotat åpen kant.** FERDIG 07.11: Jørn besluttet
alle fem punktene. Kanten bekreftet (FortiGate → caddy på raven),
invitasjonslevetid 14 dager, budsjett og betaling per DELTAKER (Vipps
kommer / Fiken-faktura etter deltakerens faktura-innstillinger),
innloggingsnøkkel per deltaker, HUD-mål fastsettes eksperimentelt.

**E2 — Designnotat: flere deltakere på samme prosjekt.** FERDIG
07.11 (`docs/2026-11-07-flerdeltaker-design.md`): arbeidsflyt-
innstilling per prosjekt (`tbd` = én skjerm, 409-vakta består;
`github-flow` = gren per deltaker, alt deles via merge),
merge-autoritet per prosjekt (utpekt deltaker i v1, utpekt LLM
reservert), deling ved milepæler, adgang følger gruppen
(invitasjonslenken er adgangen), tavla viser inntil 4 fliser med
demokratisk bytte (detaljer eksperimentelt). GitHub Flow realiseres i
produktet — deltakerne har ikke GitHub-kontoer.

**E3 — Høsting: `studio` og `mal-studio` fødes.** FØRSTE SKIVE FERDIG
07.11: treet høstet og pushet (`KODE15studio/studio`, root-commit) med
én org, arbeidsflyt/merger i registeret, betinget 409-vakt, Opper i
stedet for LiteLLM (nøkkel per deltaker når kontoen er oppe), k15s-navn
+ port 8200 + eget subnett for sameksistens med Light; `cargo check` og
frontend-bygg grønt; `mal-studio` seedet (grunnmal + fellesregler +
mal.yaml) og pushet; Handover 0 skrevet. GJENSTÅR (neste skive, listet
i `studio/handover/HANDOVER.md`): Opper-konto + verifisert Zoo-svar,
bygge/starte stacken på raven, konfetti- og presence-test grønn,
gren-regimet i flatene, tavle-taket (4), invitasjonslenker per deltaker
+ kill-switch, deltaker-budsjett.

**E4 — Måle-HUD.** Tastetrykk→skjerm, WebRTC-vei, presence-RTT.
Baseline måles FØR eksponering, så degradering etterpå leses i tall.
Budsjettmål fryses her (forslag: < 50 ms i rommet, < 120 ms remote).

**E5 — Åpen kant.** FortiGate-bestilling (norm «bestilling») for 443
→ caddy på raven; DNS `kode15.studio` i deploi-dns + LE-sertifikat
via DNS-01; `studio15.cloud` redirecter i måneder; offentlig TURN ved
behov; raven-unntaket ut av dvale-vakta. Første fremmed-wifi-test
(HIØ-scenarioet: 4 studenter + 70-tommer i samme rom).

**E6 — «Bli tavle»-knappen.** Window Management API i Chromium
(`getScreenDetails()` + fullskjerm-delegering), fallback URL + F11.
Gjør HIØ-rommet uavhengig av tavle-Pi; Pi-ens rolle revurderes når
delene kommer.

**E7 — Innlogging og betaling (eies av wordpress-drengen).**
WooCommerce i `wordpress-kode15-no` med GDPR-verktøyene i WP-kjernen;
kjøp/tildeling utsteder signert nøkkel per DELTAKER til studio —
deltakeren er betalende enhet (Vipps kommer / Fiken-faktura etter
deltakerens faktura-innstillinger; regnskaps-drengen eier
Fiken-flyten). Studio-siden bygger kun endepunktet som utsteder
invitasjonslenker mot deltakernøkkel, og holder bare visningsnavn og
uforanderlige referanser (Fiken-kontakt-ID, ordre-ID).

**E8 — Skalering.** Container swarm med flere servere og hybrid LLM
(RTX 5080/5090 bak OpenAI-kompatibelt endepunkt, f.eks. vLLM, som
Zoo-moduser peker på per modell). Startes når HUD-tall og faktisk
bruk viser behovet — ikke før.

**Løpende i Light (blokkerer ingenting):** slette
slettmeg-prosjektene, DEFA 2-retest (kodelader eier), Zoo 3.88
bevisst utsatt, FortiGate DHCP-reservasjonsordren, nybegynner trinn 2
i ferskt prosjekt for å verifisere mal-herdingen fra 06.11.

## Rekkefølgens logikk

Notater (E1–E2) før kode, fordi de endrer det som portes. Høsting
(E3) før HUD (E4), fordi HUD-en bygges i den nye stacken. HUD før
åpen kant (E5), fordi latency-prinsippet er fredet: mål først,
eksponer etterpå. «Bli tavle» (E6) før HIØ-besøk. Betaling (E7) og
skalering (E8) når produktet har brukere som krever det.
